# 硇洲岛田野图集 · Naozhou Field Atlas

[在线地图](https://naozhou-map.netlify.app/) · [GitHub 源码](https://github.com/residualsun1/NaozhouMap)

黑白矢量田野调查地图，包含村庄、道路、聚落、行政范围示意、调查点位和神明记录。

## 本地使用

Windows 双击 `打开地图.cmd`，访问 `http://127.0.0.1:8765/`，保持服务窗口开启。
本地版继续使用 PowerShell 服务，记录保存在本机 `data/` 文件夹。
人物、神明、信仰及田野日志的本地保存需要 Node.js 22 或更新版本；更新本地服务后请重新启动「打开地图.cmd」。
新克隆的仓库不含私人调查存档；本地首次启动需准备自己的 `data/field-points.geojson` 和 `data/village-faith.json`，或继续使用已有工作文件夹。

## Netlify 部署

1. 在 Netlify 导入本 GitHub 仓库，生产分支选择 `main`。
2. 构建命令 `npm run build`，发布目录 `dist`，函数目录 `netlify/functions`，配置已写入 `netlify.toml`。
3. 添加环境变量 `NAOZHOU_EDITOR_PASSWORD`，使用至少 20 位的独立口令，作用域包含 Functions。口令不可提交到 GitHub。
4. 部署完成后，进入地图「数据 → 登录编辑」输入口令，即可保存至云端。

云端资料使用 [Netlify Blobs](https://docs.netlify.com/build/data-and-storage/netlify-blobs/) 的站点存储，重新部署不会清空记录。记录保留现有 ID、坐标和版本冲突检查。
公开资料可供访客阅读；非公开人物与日志只对授权编辑者开放。浏览器使用 12 小时的 HttpOnly 会话。

### 自主设置编辑口令

进入地图「数据 → 登录编辑」，登录后点击「更改口令」，填写当前口令与自己选择的 8–128 字符新口令。神明谱系和人物档案页面的登录区域也有相同入口。更改后当前设备保持登录，旧口令和其他设备的旧会话失效。

自定义口令以随机盐及 scrypt 哈希存入独立云端凭据集合，不写入源码或田野资料；环境变量继续作为服务端签名密钥，保留原配置即可。本地 PowerShell 版无需口令，行为不变。
本地文件与云端存储是两份资料，不会自动双向同步。可用页面的 GeoJSON / 信仰备份导入导出迁移。
`netlify/seed/` 保存首次上线的公开资料；云端已有记录后，后续发布不会用种子资料覆盖它们。

后续修改源码后提交、推送到 `main`，Netlify 自动重新部署。在线新增的调查资料不会自动变成 Git 提交。

## 开发

```sh
npm ci
npm test
npm run build
```

主要文件：`index.html`、`map.css`、`map-app.js`、`faith-records.js`、`map-data.js`。
`cloud-access.js` 只在 Netlify 构建中启用；`netlify/functions/` 提供 `/api/points`、`/api/faith`、`/api/archives` 和 `/api/auth`。
村庄「基本情况」由 `place-archives.js` 编辑，线上存入独立云端档案，本地存入 `data/place-archives.json`。数据面板可导入、导出原档案备份。调查点位原有笔记仍通过点位表单编辑和保存。

### 田野日志

村庄档案的「田野日志」支持多条纯文本记录、观察日期（日／月／年／待考）、类型、标签、来源与年份／类型筛选。`field-journal.js` 通过稳定地点 ID 和地点种类关联；`/api/field-entries` 逐条保存、编辑或删除，沿用 revision、条件写入和原编辑登录。云端集合为 `field_entries`，本地文件为 `data/field-entries.json`；本地服务更新后需重新启动「打开地图.cmd」。

新日志默认仅授权编辑者可见，公开必须明确确认；未登录的云端请求只能读取公开日志。当前共享编辑口令不区分个人，因此本期没有声称为某位研究者独享的私人草稿。日志不会写入浏览器公共缓存或静态发布目录。

旧档案和调查点位笔记仍保留原字段，作为「日期未注明」的历史笔记展示。可主动整理为日志并补日期，以来源指纹避免同一旧笔记重复显示；不自动迁移、覆盖或清空原文。信仰资料的访谈笔记仍留在信仰分区。日志预留稳定神明 ID 引用，不推断空间流动。

### 展开阅读

村庄标题区的「展开阅读」打开全屏档案，桌面提供左侧目录，手机使用顶部目录。`place-reader.js` 将原档案节点暂时移入阅读容器，保留同一份数据、筛选和编辑事件；返回后恢复原面板滚动与抽屉状态。编辑入口返回现有表单，不另建保存流程。

`?placeKind=reference&placeId=…&view=reading` 可直接打开完整档案，调查点位使用 `placeKind=survey`；支持刷新、浏览器返回与前进。新章节只需在现有分区增加 `data-reading-label` 和稳定的元素 ID，目录即会纳入可见分区。

### 神明谱系

地图工具栏的书册入口打开「神明探索」：桌面使用约 34vh 的底部横向图录，支持滚动浏览、名称／别名检索和神函筛选；选中卡片后保留图录，并在下方显示关联村庄与完整档案入口。卡片图片区暂显示「暂无图片」，不使用模拟神像替代真实资料。手机继续使用可展开、收起的底部抽屉。`deity-explorer.js` 复用现有总库和信仰记录，只读查询，按地点 ID 去重；缺少坐标的关联仍保留在列表，不生成点位。点击村庄切换到原地点档案。

抽屉中可打开完整 `/deities` 工作台。总库支持八类地方神函、多神函归属、待分类、别名检索、建档、编辑及归档；同名档案由不同 ID 区分。初始总库为空，不按历史名称自动建档或合并。八类原始索引保留名称和 ID，可增补其他神函、编辑增补项。地图与完整档案通过神明 ID 双向跳转；同一标签页返回时，以会话状态恢复神明选择和地图视角，不写入田野资料。

`/api/deities` 返回 `{version:1,revision,titles,records}`，沿用编辑登录与 revision 冲突控制。线上使用独立的 `deities` 存储，本地存入 `data/deities.json`。归档保留神明 ID 和已有村庄关联，不做级联删除。

信仰记录原有 `deities` 数组及其他字段保留，兼容增加 `deityLinks: [{id,deityId,nameIndex,localName,localTitle}]`；`nameIndex` 对应原数组位置，引用只通过 `deityId` 建立。同名可对应不同 ID，同一 ID 可跨村庄、宫庙或记录引用。旧客户端省略关联字段时，后端保留已有关系；如果同时改动已关联的名称或村庄则拒绝保存，要求刷新。没有关联的旧记录始终有效。

总库详情按 ID 动态汇总 `/api/faith` 的村庄与记录；共享的 `DeityAtlas.villagesFor()` 和 `mapURL()` 可供后续地理展示使用。`/?placeKind=reference&placeId=…&faithId=…` 可定位地点及原记录；调查点位使用 `placeKind=survey`。这些关系不代表轮祀或流动方向。

总库页面可导入、导出 JSON；信仰备份包含完整关联，CSV 也列出神明 ID 和当地信息。恢复到其他项目时先导入神明总库，再导入信仰记录；同编号的现有资料保留。
发布目录仅包含运行所需文件，本地备份、访谈存档和工作截图不上传到网站。

### 人物探索与档案维护

地图顶部「人物」打开轻量人物探索，复用人物总库，按地点 ID 汇总居住、活动、仪式主持等实际关联。桌面使用底部横向卡片，手机使用底部抽屉；与神明探索互斥，不生成活动路线。完整 `/people` 工作台支持姓名／法号／别名检索、多身份筛选、建档、编辑、村庄与日志关联。新建人物默认仅编辑者可见，真实姓名及内部研究备注不随公开档案自动公开。

人物和神明工作台提供归档、恢复、人工合并与无引用档案的永久删除。合并前必须选择主档案 ID、逐项处理字段差异并确认；原 ID 保留跳转，引用按 ID 转移，日志正文不改写。人物合并使用双方中较私密的公开范围。仍有引用的档案须先解除关联，或改用归档、合并。

`/api/archive-management` 仅供已登录编辑者使用，提供引用预览、维护操作和计数。四类关联资料使用不可变快照及单一版本指针提交，防止合并一半或旧客户端恢复已删除的编号。既有资料首次读取不迁移、不覆盖；本地后续快照保存在 `data/.archive-store/`，应连同整个 `data/` 文件夹保存。旧来源文件及历史快照仍保留，因此这里的永久删除表示从当前总库移除，不等同于历史存储的隐私抹除。
